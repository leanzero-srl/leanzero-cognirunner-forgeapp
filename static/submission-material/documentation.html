Overview

CogniRunner brings real AI understanding to Jira workflows. Jira's built-in validators only do structural checks — "field is required", "matches regex". CogniRunner reads the actual meaning of your fields, attachments, and issues, then validates, decides, generates content, and takes action — on every transition, on any of the 68 Jira product events, or on a schedule. Describe what you want in plain English — no scripting.

Six rule types cover the full loop — four on workflow transitions, two that run without one:

  • Validators block a transition when field content fails your rule, showing the user the AI's reasoning.
  • Conditions hide a transition entirely when criteria aren't met — the user never sees the button. Conditions are evaluated by Jira itself, so they run on a deterministic check rather than an AI prompt: no per-transition cost, no latency, and enforced on every surface including REST and automation.
  • Semantic Post-Functions run after a transition: the AI reads a field, decides, generates a value, and writes a target field — e.g. summarize the work into Release Notes.
  • Static Post-Functions let the AI generate JavaScript once, then run it at zero AI cost on every transition — chaining up to 50 sandboxed steps.
  • Listeners react to Jira events instead of transitions — issue created, comment added, sprint started, version released, and the rest of the 68 events Forge exposes for Jira, Jira Software and JSM — filtered by project, issue type, JQL, changed fields or a comment regex, and gated by an optional plain-language AI condition. See Listeners.
  • Scheduled Jobs run on a cron expression in any IANA time zone — once, or once per issue of a JQL scope, the way an escalation service does. See Scheduled Jobs.

Listeners and jobs execute either code steps — the same AI-generated, sandboxed JavaScript as static post-functions — or an AI agent given plain-language instructions and an allow-list of actions (see AI Agent Mode). Both can be provisioned from CI or a migration script through the bearer-token Rules REST API.

Not everything needs a model. CogniRunner also ships roughly 27 premade deterministic validator and condition types — field required, field must be changed, regex pattern, length bounds, allowed values, relative dates, comment required, attachment required, all sub-tasks resolved, and more. They evaluate instantly and run at zero AI cost.

CogniRunner works across company-managed and team-managed Jira projects, supports all standard, custom, and many third-party field types, analyzes the content of attached files and images, and runs on your choice of AI provider — bring your own key, or use the zero-key Atlassian Forge LLM.

Getting Started

CogniRunner integrates into Jira's native workflow editor. Validators, conditions and post-functions are added there (or through the Add Rule wizard); listeners and scheduled jobs are not tied to a transition, so they live in the admin panel under Apps → CogniRunner → Listeners / Scheduled Jobs — see Listeners and Scheduled Jobs. To add a validator or condition:

  1. Open your workflow in the Jira workflow editor Select a transition and click the Rules panel on the right side. You'll see rule categories: Restrict transition, Request input, Validate details, and Perform actions.
  2. Add a new rule Click the + button next to "Validate details" (for validators) or "Restrict transition" (for conditions). In the "Add rule" dialog, find CogniRunner Field Validator — or, for conditions, CogniRunner Field Condition — under the Marketplace Rules section.
  3. Pick a type and configure For a validator or post-function, select the field, describe your criteria in plain English, and optionally attach context documents. For a condition, pick one of ten deterministic checks — no prompt, no AI (see Deterministic Conditions). Click Update to save.

Prefer not to touch the workflow editor? Open Apps → CogniRunner and use the + Add Rule wizard. Pick a project, workflow, transition, and rule type, configure it, and CogniRunner injects the rule into the workflow for you.

Configuring a Validator

When you add or edit a CogniRunner AI validator, you'll see the configuration form with three core settings:

  1. Field to Validate — which Jira field the AI should evaluate
  2. Validation Prompt — your criteria described in natural language
  3. Jira Search (JQL) — how agentic search behaves (auto-detect, always on, or off)

You can also attach context documents from the Documentation Library so the AI evaluates against your API contracts, schemas, and business rules. A built-in Test Run evaluates the rule against a real issue before you publish, and AI Review analyzes the configuration and suggests improvements.

Deterministic Conditions

Conditions decide whether a transition is shown at all — and in CogniRunner they are fully deterministic. A condition never calls an AI: you pick one of ten checks, and Jira itself evaluates it. That means zero AI usage, zero per-transition cost, and no added latency. And because Jira does the evaluating, the condition is enforced on every surface — the issue view, the REST API, automation rules, and bulk operations alike.

The ten checks:

  • Issue type is…
  • Issue is resolved
  • Resolution is…
  • Priority is…
  • Parent issue status is… — works for sub-tasks too
  • Current user is the assignee
  • Current user is the reporter
  • Field has a value, Field is empty, and Field equals a value — three checks on custom fields

The assignee and reporter checks are a condition-only capability: Jira's expression engine sees the acting user at evaluation time, which a validator cannot.

Field checks — custom fields, per kind

The three field checks work on custom fields of verified kinds. Equals comparisons are case-insensitive.

Custom field kindHas a value / is emptyEquals a value
Text (single line), URL, dateYesYes — case-insensitive; dates as YYYY-MM-DD
NumberYesYes — numeric comparison
Select, radio buttonsYesYes — compares the option's value, case-insensitive
Paragraph, date-time, user, group, cascading select, version, projectYes—
Labels, multi-select, checkboxes, multi-user, multi-group, multi-versionYes—

Two honest caveats. A field hidden by a field configuration (or whose context doesn't cover the project) reads as empty. And an empty field never hides an equals check — combine it with "Field has a value" when it should. When you want a blocked transition with a message rather than a hidden button, use a validator instead.

Because Jira evaluates conditions natively, they produce no execution-log entries — no app code runs on the transition. See Execution Logs.

Upgrading from an earlier version? Old AI-prompt-shaped conditions never actually gated a transition. Opening one now shows the original prompt, says plainly that it never ran, and offers a one-click conversion to a deterministic check. Existing rules are left untouched, and unrecognized configs fail open (the transition stays visible) rather than blocking anyone.

Field Selector

The field selector dropdown shows all fields available on your project's edit/view screens, grouped by system fields and custom fields. Each entry shows the field name, its internal ID, and its type. The dropdown is context-aware: it resolves the project's screen scheme chain to show only the fields that are actually present on the transition screen.

You can search for fields by name using the search box at the top of the dropdown. The selected field determines what content the AI receives for validation. The picker is also honest per rule type: in the condition editor, fields that deterministic conditions can't check are explicitly annotated rather than offered and ignored.

When you select Attachment, CogniRunner downloads and analyzes the actual content of attached files — not just the filename. See Attachment Content Analysis for supported formats.

Writing Validation Prompts

The validation prompt is where you describe your quality criteria in natural language. The AI evaluates the field content against this prompt and returns a pass/fail result with reasoning.

Good prompts are specific and describe what the content should or should not contain:

  • "The description must include clear steps to reproduce, the expected behavior, and the actual behavior. Reject vague one-line descriptions."
  • "Acceptance criteria must be written in Given/When/Then format with at least one testable condition."
  • "Check whether a similar or duplicate issue already exists in this project, and explain the match if you block the transition."
  • "The attached design must be a UI screenshot or mockup, not a stock photo or unrelated image."
  • "Reject the transition if the field contains profanity, PII, or placeholder text such as 'TBD' or 'WIP'."

The AI's response is always shown to the user when validation fails, so writing prompts that ask the AI to "explain clearly" will produce better error messages.

Agentic Validation & Duplicate Detection

When a validator's rule needs context beyond the field itself, CogniRunner goes agentic: the AI autonomously builds and runs JQL queries against the issue's own project — over multiple rounds — to find similar or related work before deciding. (Agentic search is a validator capability — deterministic conditions never call an AI.) The Jira Search setting has three modes:

ModeBehavior
Auto-detect from prompt CogniRunner analyzes your prompt text and automatically enables JQL search if it mentions duplicates, similarity, existing issues, or cross-referencing. This is the recommended setting.
Always enabled JQL search is always active, regardless of prompt wording. The AI can run up to 3 rounds of JQL queries to find related issues.
Always disabled No JQL search is performed. Validation is based solely on the field content and prompt. Fastest option.

When agentic search is active, the AI generates and executes JQL queries to find related issues. It can run up to 3 rounds of queries, each returning up to 10 results, and is automatically confined to the rule's own project for safety. The AI then uses what it finds to inform the decision — and the full query trail is logged.

Agentic search adds latency to the validation (up to roughly 22 seconds in the worst case). If the budget runs out, the transition is allowed (fail-open) rather than blocked indefinitely. For simple validations that don't need cross-referencing, use "Always disabled" for the fastest response.

Validation in Action

When a user attempts a workflow transition, CogniRunner evaluates the configured field against your prompt. If validation fails, the transition is blocked and the AI's reasoning is displayed as an error message directly on the transition screen.

The error message always includes:

  • A clear statement that AI Validation failed
  • The specific reason for the failure
  • When agentic search was used: references to related issue keys
  • Enough context for the user to understand what needs to change

Semantic Post-Functions

Validators check; post-functions act. A semantic post-function runs after a transition completes: the AI reads a source field, decides whether to act, generates a value, and writes it to a target field — all described in plain English. It has three parts:

  • Condition — when should this run? The AI evaluates the source field and decides to update or skip. Use "Run every time" for an always-on fast path.
  • Action — what should it write? The AI generates a value to the rules you describe.
  • Target field — where does it go? Schema-aware formatting writes the value into the field you choose.

Example Actions

  • "After transition to Done, summarize the description into the Release Notes field."
  • "When moving to Code Review, extract the acceptance criteria into a checklist."
  • "On every transition, append the status change and timestamp to an audit-trail field."

Before calling the AI, CogniRunner runs a pre-flight check via the editmeta API to confirm the target field is editable on the issue — and if it isn't, it stops with a clear explanation and lists the fields that are editable. AI-generated values are auto-formatted to match the field schema (select fields get {value: "..."}, numbers are converted, labels become arrays), and exact Jira error messages are parsed into actionable fix guidance on failure.

Post-functions run after a transition succeeds and never block it (fail-open by design). Any errors are recorded in the execution log with a recommendation, so you can diagnose them without disrupting users.

Static Post-Functions & AI Actions

For deterministic automation, the AI writes JavaScript once at setup. After that it runs on every transition at zero AI cost. Chain up to 50 steps with variable passing between them, a built-in code editor with api.* autocomplete, per-step retries with backoff, and a sandboxed Jira API.

OperationWhat it does
JQL SearchQuery Jira for related issues.
Jira REST APIRead or write any Jira resource (GET, POST, PUT, DELETE, PATCH).
External APICall allow-listed external services and webhooks.
Confluence APICreate or update Confluence pages.
Debug LogInspect values while you build.

Describe each step in plain English, click Generate, and the AI writes the JavaScript into a CodeMirror editor with syntax highlighting and autocompletion. Steps chain via ${variableName} references, and a Test Run executes against real Jira data — reads are real, writes are simulated — so you can verify behavior before publishing.

The same engine powers declarative AI actions — add an AI-drafted comment, create a sub-task or linked issue, generate and attach a real DOCX/PDF/PPTX, or use the Research & Document flavor: it gathers evidence from web search and documentation lookups, has the AI author a grounded brief, and attaches it to the issue — all configured in plain English, no code required.

Rule Management (Enable / Disable / Delete)

Each CogniRunner rule can be enabled or disabled without removing it from the workflow. This is useful for temporarily pausing validation during migrations, bulk updates, or troubleshooting. For validators and post-functions, disabled rules are skipped at runtime (fail-open) and their configuration is preserved. For conditions, the toggle goes further: because Jira itself enforces conditions, disabling one writes the disabled state into the workflow rule itself — so "Disabled" is never a lie. If that workflow write fails, the toggle refuses rather than half-applying. Listeners and scheduled jobs have the same Enable / Disable / Delete controls on their own tabs (and over the Rules REST API): a disabled listener stops matching events, and a disabled job stops running on its schedule but can still be run manually.

Delete — and actually detach

Deleting from the Rules tab (per row, or in bulk via checkboxes) does more than remove a list entry: it also detaches the rule from its Jira workflow transition, so it genuinely stops running. Before anything happens, a preview dialog predicts the outcome per rule — flagging rules already gone from the workflow, duplicates, and workflows shared by multiple projects — and offers a lighter alternative, Remove from this list only, which leaves the rule attached and running.

Import & Export

Rules travel. Export produces a self-contained JSON file — including the full JavaScript code of static post-functions — that you can keep in version control or move to another site. Import shows a preview of what will be created and lets you rebind fields to the target site's fields (custom field IDs rarely match across sites) before anything is written.

Listeners (Jira events)

Until now everything on this page ran when an issue crossed a workflow transition. A listener reacts to a Jira event instead — any of the 68 product events Forge exposes for Jira, Jira Software and Jira Service Management. When an event matches the listener's filters and its optional AI condition, the listener runs either code steps (the same sandboxed api.* surface as static post-functions, bound to the event's issue) or an AI agent (see AI Agent Mode). Listeners live in the admin panel under Apps → CogniRunner → Listeners, and can also be pushed as JSON through the Rules REST API.

Issue viewed fires on every issue view and is flagged HIGH VOLUME in the picker. Events arrive asynchronously — seconds typically, up to roughly three minutes worst case — so a listener is eventually consistent, and a freshly saved listener can take up to 30 seconds to start matching.

Configuring a listener

Click + Add Listener. The editor has a name, an optional description, and these parts:

  • When these Jira events fire — pick one or more events from the grouped picker.
  • Only when… — filters: Projects, Issue types, Changed fields (applies to "Issue updated" only: fire when at least one of these fields is in the changelog), Comment matches (regex) for comment events, and Issue matches JQL (one search per event).
  • Ignore events caused by this app — the loop guard, on by default. It prevents the classic automation loop where a listener's own writes re-fire it.
  • AI condition (optional) — a plain-language yes/no the model evaluates before the run, one AI call per matching event. If the condition is not met, or the AI evaluation fails, the listener is skipped — it fails closed. Leave it empty to run whenever the filters match.
  • What happens — Code steps or AI agent. Code steps use the same Function Builder as static post-functions: describe, Generate, Test, Fix with AI. Actions run as the CogniRunner app, using its Jira permissions — never as the triggering user.
  • Simulation mode (reads are live, writes are logged but never executed), Suppress notifications on field updates (needs project admin; falls back to notifying), and Enabled.

The current issue — and when there isn't one

Inside code steps, api.context carries runtime ("listener"), the current issueKey, the eventType, and event — the raw Forge payload. Issue-bound helpers (addComment, addLabels, transitionByName…) act on the event's issue. For events that have no issue — a version released, a sprint started, a project archived — the current issue is null, and those helpers throw a clear error rather than guessing. Use api.forIssue("KEY") to re-bind the whole surface to any issue you choose. The code generator and the fixer are told all of this, so generated steps use the right shape for the events you picked.

Test with an issue, and the last real payload

The Test listener card lets you test with an issue before anything fires: pick an issue and one of the listener's events, click Run test, and CogniRunner builds a synthetic event from that real issue and runs filters, AI condition and actions in simulation — reads are live, writes are recorded, and no real Jira event is triggered. Once an event has actually fired on the site, Show last real payload reveals a redacted sample of the exact api.context.event shape (kept for seven days per event type, with rich-text bodies removed), so you can write code against what Jira really sends.

Brakes. A test never exercises event delivery, the brakes, or the self-event guard. At runtime, a listener that keeps re-firing hits two backstops: at most 30 runs per issue and 120 runs per listener in any fixed five-minute window. When a brake trips it is logged once, and further runs in that window are suppressed silently. Keep "Ignore events caused by this app" on unless you have a specific reason not to.

Every accepted event is claimed at least once, so a redelivered event never runs twice. Queued and running listener runs appear in the Active Jobs panel of the Execution Logs tab, where they can be cancelled — the kill switch. Runs get a 105-second budget inside the 120-second async consumer (the 25-second trigger itself only matches and queues), and each one lands in the execution log as type Listener, with the event that fired.

Scheduled Jobs (cron)

A scheduled job runs on a cron schedule — once per schedule with no current issue, or once per issue of a JQL scope, the way an escalation service does — executing the same code steps or AI agent as a listener. Jobs live under Apps → CogniRunner → Scheduled Jobs and can be provisioned through the Rules REST API.

Schedule

The schedule picker offers presets — Every 5 minutes, Every 15 minutes, Every 30 minutes, Every hour, Every day at…, Weekdays at…, Weekly on…, Monthly on day… — and Custom cron for anything else. Custom schedules are standard 5-field cron (minute hour day month weekday) with *, ranges, lists, steps, and month or weekday names (MON, JAN). Every schedule has an IANA Time zone, and the picker shows the schedule in words plus its next due times in that zone before you save.

The effective granularity is the platform's five-minute tick: * * * * * runs once per tick, and execution starts after the next scheduler check plus any queue delay. A job that missed ticks (an outage, say) replays at most one hour and one run — duplicate ticks are idempotent per minute and can never double-run a job.

Scope

Scope (optional) — run once per issue matching this JQL. Give the job a JQL and a Max issues cap (up to 100), and it runs once for each matching issue with that issue as the current issue, sharing the run budget across them. Leave the scope empty and the job runs once per schedule with no current issue (api.context.issueKey is null): search for issues with api.searchJql() and act on them through api.forIssue(key) — the code generator is told this too. Keep runs idempotent (check for a marker before writing) so a retried run never duplicates a comment.

Save & run now, and the run report

Jobs don't wait for the clock. Save & run now in the editor (or Run now on any saved row) queues an immediate manual run on the background worker and polls it until it finishes. The editor says exactly what that will do: with Simulation mode on, it simulates the job — live reads, writes recorded; with it off, it executes real Jira writes. A disabled job still runs manually; it just stays off the schedule.

The run report that comes back shows a PASS / SKIPPED / FAILED badge, the duration and tokens used, the reason, a chip per scoped issue (green or red, with its outcome on hover), the tool calls an agent made, the list of changes — marked simulated — nothing written in simulation — and the full log lines. A scoped run reports how many issues were processed OK, how many changed, and how many failed or were cancelled; cancelling a run keeps the work already done and marks untouched issues as not processed. The same report is stored in the execution log as type Scheduled Job, with the scheduled time, whether it was manual, and whether it was a missed-tick replay.

AI Agent Mode

Both listeners and scheduled jobs offer a second way to say what happens: instead of generating code, write instructions for the AI agent in plain language and tick the allowed actions. The model reads the event or job context — passed as fenced, untrusted data, never as instructions — and can act only through the actions you ticked. Each tool call runs through the same sandbox as code steps: simulation mode, the kill switch, the change ledger, and transient retries all apply. Rounds are capped by Max tool rounds (1–8, default 5). The agent's summary and every tool call land in the execution log and the run report.

The actions — three read-only, ten that write, plus Finish, which is always available and ends the run with a one-to-three-sentence summary and an outcome of done, nothing_to_do, or failed:

search_issues — Search issues (JQL)readRun a JQL search; up to 50 results with key, summary, status, type, priority, assignee, updated.
add_comment — Add a commentwritePost a plain-text comment; on JSM it can be an internal note not visible to customers.
update_fields — Update fieldswriteSet one or more fields in Jira REST field format.
add_labels — Add labelswriteAdd labels (existing labels are kept).
remove_labels — Remove labelswriteRemove labels from an issue.

A new agent starts with get_issue, search_issues and add_comment ticked. Issue references in tool arguments are validated before dispatch — a key like PROJ-123 or a numeric id, never an issue object — so a model that serializes the wrong shape cannot write to the wrong place or silently fall back to the current issue. The agent runs on whichever AI provider you configured — Anthropic, OpenAI, Azure OpenAI, OpenRouter, AWS Bedrock, LM Studio, or the Atlassian Forge LLM (see Multi-Provider AI).

Start every agent in Simulation mode and read the run report: it lists each tool call and every change the agent would have made. Tick write actions one at a time, and only the ones the instructions actually need.

Rules REST API

The Rules REST API is a bearer-token web trigger for pushing and driving listeners and scheduled jobs from CI, migration scripts, or a test harness — without the admin UI. It is separate from provisioning workflow rules: validators, conditions and post-functions attach through Jira's own workflow REST API, while listeners and jobs belong to the CogniRunner installation and use this one.

API access

Open Settings → API access (admin only). The panel shows this installation's Endpoint URL with a Copy button, a + Create token field, and a table of live tokens with name, prefix, created and last-used times, and a Revoke button. A new token is shown once — copy it then; only its SHA-256 hash is stored, and revoking it returns 401 to any script still using it immediately. Up to 25 live tokens can exist at a time.

Tokens look like cgr_ followed by 48 hex characters. Send one on every request as Authorization: Bearer cgr_… or as an X-Api-Key header. A missing or invalid token gets 401 { "error": "unauthorized" } with no further detail. Rows created through the API carry createdBy: "api:<tokenId>", so the admin panel shows which token made them.

Endpoints

Forge web-trigger URLs are fixed, so the resource travels in the query string:

Status codes are deliberate: a single item that saves returns 201; an array (or an upsert) returns 200; a batch in which some rows failed returns 207 with the saved rows and an indexed errors array — inspect both before marking the batch done; a validation failure returns 400 { "error": "…" } with the same message the admin UI shows; no or bad token returns 401. Run now returns 202 with a taskId to poll under ?resource=tasks.

Example

Use the Rules API URL shown for the target installation. Save either configuration below as a JSON file and send it with a token from that installation:

curl --fail-with-body "$RULES_API_URL?resource=listeners" \
  -H "Authorization: Bearer $RULES_API_TOKEN" -H 'Content-Type: application/json' \
  --data-binary @listener.json
curl --fail-with-body "$RULES_API_URL?resource=jobs" \
  -H "Authorization: Bearer $RULES_API_TOKEN" -H 'Content-Type: application/json' \
  --data-binary @job.json

Read the returned id back with GET ?resource=listeners&id=… (or jobs) to verify the complete saved configuration. For provisioning reruns, include that id and the complete configuration in the POST to update the same rule; use PUT for a partial update.

  "mode": "agent",

}

The complete guide — the run pipelines, storage keys, limits, and the live test scripts — is in LISTENERS-AND-JOBS.md in the repository.

Admin Hub

The CogniRunner Admin panel is the hub for every rule across your Jira workflows — and for the listeners and scheduled jobs that run outside them. Access it from Apps → CogniRunner in the Jira sidebar. It has tabs for Rules, Listeners, Scheduled Jobs, Execution Logs, Documentation, Skills, Memories, Permissions, and Settings, plus an Add Rule wizard.

  • All rules, one place — every validator, condition, and post-function across all workflows, with type and ownership filters (All Rules / My Rules), inline enable/disable, and per-row or bulk Delete. Listeners and scheduled jobs are not workflow rules, so they get their own tabs with the same enable / disable / delete controls, a Last run column, and expandable recent executions per row.
  • Registry usage meter — a byte-accurate meter shows real pressure against the registry's capacity (500 rules / 240 KB), so imports and REST provisioning know exactly how much room is left.
  • Owner column — every rule shows its author, and "My Rules" strictly means rules you authored. Rules claimed from workflow scans are recorded with an explicit Unowned chip rather than mis-attributed — claiming is not authoring.
  • Scan workflows → Register all — sweeps every workflow for rules attached outside the panel (REST automation, imported or copied workflows), claims them so they can be managed, and reports anything it skipped.
  • Automating rule creation — a panel on the Rules tab exposes everything needed to provision rules over Jira's REST API: this installation's extension ARIs with copy buttons, plus the ruleKey and target slot per rule type. See Provisioning Rules over REST.
  • Add Rule wizard — create a rule without touching the workflow editor: pick project, workflow, transition, and type, then configure and publish. CogniRunner injects the rule into the actual Jira workflow for you.
  • Knowledge & Skills — a shared documentation library, reusable Skills, and learned Memories give the AI grounded, instance-specific context.
  • API access — an admin-only panel on the Settings tab mints and revokes bearer tokens for the Rules REST API, and shows this installation's endpoint URL.

Provisioning Rules over REST

CogniRunner rules are ordinary Forge workflow rules, so you can attach them with Jira's own workflow REST API — using your Jira credentials, not a CogniRunner API. Read the workflow with GET /rest/api/3/workflows/search, add the rule to the transition, and write it back with POST /rest/api/3/workflows/update. That is how you bulk-provision rules across many projects, migrate them between sites, or keep them in version control.

Everything install-specific comes from the Automating rule creation panel shown above: this installation's extension ARIs (with copy buttons — the environment id inside each ARI is unique to your install, so never copy one from an example), the ruleKey and target slot per rule type, and the size caps (a rule's config must stay under 32 KB, and the registry meter shows how much room is left).

Rule typeruleKeyGoes in
Validatorforge:expression-validatortransition.validators
Conditionforge:expression-conditionthe transition's conditions tree
Semantic & static post-functionsforge:workflow-post-functiontransition.actions

Two things catch people out. A rule attached over REST runs immediately but is invisible to the admin panel until you claim it — use Scan workflows → Register all afterwards. And every rule needs a stable id embedded in its config: without one it can be claimed but never disabled from the panel, and removing it from the workflow becomes the only off-switch.

Field-condition configs carry two extra keys the admin UI normally resolves for you: exprProp (the custom field id the Jira expression indexes) and exprKind (the comparison strategy — plus valueNum as a JSON number for numeric equals). A mismatched exprKind is the one way a hand-crafted config can fail closed and hide the transition, so copy configs the UI produced rather than hand-writing these.

The full guide — payload shapes, the config schema per rule type, and a worked end-to-end example — is in REST-API-RULES.md in the repository.

Two REST paths, two kinds of rule. Everything on this page attaches to a workflow transition, so it travels through Jira's workflow REST API with your Jira credentials — CogniRunner never needs to be in the loop. Listeners and scheduled jobs are different: they are not workflow rules, they belong to the CogniRunner installation, and Jira has no API for them. Those are provisioned through CogniRunner's own bearer-token Rules REST API — a web trigger whose URL and tokens come from Settings → API access. Use the Jira workflow API for validators, conditions and post-functions; use the Rules REST API for listeners and jobs.

Permissions & Roles

Control who can do what with a role and scope model. Jira site administrators always have Admin access, the first user is bootstrapped as Admin, and the last admin is protected from removal or demotion.

RoleWhat they can do
ViewerView rules and execution logs.
EditorCreate, edit, disable, and manage rules and documents.
AdminFull access, including permissions and AI provider settings.

Each role is paired with a scope — own rules or all rules — so you can delegate without handing over the whole app. An editor scoped to "own" can only edit the rules they created; scoped to "all" they can manage everyone's. Execution logs and rule export honor the same model: what you can see and export is bounded by your role and scope.

Documentation Library, Skills & Memories

Give the AI grounded context. Upload API docs, JSON schemas, business rules, or code snippets once, then attach them to any rule so the AI validates and generates against your standards — not just its training data. Each document is categorized (API Documentation, JSON Schemas, Business Rules, Field Mappings, Code Snippets, General) and JSON, XML, YAML, and JavaScript are auto-formatted on preview.

Beyond documents, reusable Skills and learned Memories give the AI grounded, instance-specific knowledge that carries across rules — so your validations and generated content reflect how your team actually works.

Execution Logs

Every validator, post-function, listener and scheduled job run is logged with full context: pass/skip/error status, whether it ran live, from the async queue, or as a test, the AI's reasoning, the JQL it ran, and an execution trace. Deterministic conditions produce no log entries — Jira evaluates them natively, so no app code runs. Logs are available in the Admin panel's Execution Logs tab, in the individual rule view, and — for listeners and jobs — as expandable recent executions on their own tabs. Listener entries record the event that fired; scoped job entries record a per-issue outcome for every issue in the scope.

Each log entry includes:

  • Status — PASS, SKIP, or ERR badge
  • Rule type — Validator, Post-Function (semantic / static), Listener, or Scheduled Job
  • Source chip — LIVE (a real transition), QUEUED (the async queue), or TEST (a dry run from the editor)
  • Honesty flags — DRY-RUN when writes were simulated, FAIL-OPEN when an error let the transition through instead of blocking it
  • Issue key & duration — which issue ran, and how long it took
  • AI reasoning — the full explanation from the AI
  • JQL queries — the queries executed during agentic search
  • Trace & recommendations — a step-by-step trace and AI-generated fix suggestions on failure

Logs are stored in Forge storage with a maximum of 50 entries (FIFO — oldest entries are removed when the limit is reached). Logs can be cleared from the admin panel.

You don't have to open the admin panel to see activity: the CogniRunner on this issue panel in the issue view shows a read-only glance of recent rule activity for the issue you're looking at.

Multi-Provider AI (Bring Your Own Key)

CogniRunner ships with no embedded API key — and no key is ever required. Connect your own provider — Anthropic, OpenAI, Azure OpenAI, OpenRouter, AWS Bedrock, or a local LM Studio — or use the zero-key Atlassian Forge LLM that runs inside Atlassian's platform with no external egress. Each provider stores its own key, so switching providers never loses your settings.

ProviderNotes
AnthropicClaude models, your key
OpenAIYour OpenAI API key
Azure OpenAIYour Azure deployment endpoint
OpenRouterOne key, many models
AWS BedrockConverse API, your account
LM StudioSelf-hosted local models on your own hardware
Atlassian Forge LLMZero-key — runs inside Forge, no external egress

With LM Studio, inference runs on your own hardware — and CogniRunner's multi-model pool spreads validator calls across every model you have loaded, so no single local model becomes the bottleneck.

Configure your provider in the Settings tab of the admin hub: choose a provider, paste your key (stored encrypted in Forge KVS and never sent to the frontend — only a masked indicator is shown), and pick a model. Providing a key unlocks model selection from that provider's model list. Removing a provider's key leaves the others untouched.

Your field and attachment content is sent only to the AI provider you configure. With the Forge LLM provider, requests stay within Atlassian's platform — no external egress; with LM Studio, they go to your own hardware. CogniRunner stores no issue or field content beyond short truncated excerpts in the capped 50-entry execution log — your rules, documents, skills, and memories live in Forge storage on your own site.
